# エージェント開発ハーネス（v1）

Local Deck AI では、エージェントに単発の実装を依頼するだけでなく、**意図・制約・検証・記録**をリポジトリ内に置き、同じ品質で反復できるようにする。これをハーネスと呼ぶ。そのハーネスを、タスク発見から検証・学習まで繰り返す運用がループである。

この v1 は自律実行基盤やスケジューラを導入しない。まず、1 変更を安全に完了できる最小ループを、ローカル開発と CI で同じ形にする。

## このリポジトリのハーネス

| 要素 | 実装 | 役割 |
| --- | --- | --- |
| コンテキスト地図 | `AGENTS.md` と `docs/` | 必要な規約を段階的に読めるようにする |
| 境界・契約 | Zod スキーマ、入力検証、既存テスト | LLM・GUI・CLI の不正な入力を早期に止める |
| 検証器 | `npm run verify` | lint → test → smoke → build → package dry run を一貫して実行する |
| 外部の品質ゲート | GitHub Actions と PR テンプレート | ローカル結果と CI 結果を比較可能にする |
| 永続的な記憶 | コード、テスト、`docs/`、Git 履歴 | 同じ失敗や判断を次回のエージェントに残す |

`npm run verify` が通ったことは重要な証跡だが、要件そのものを満たす証明ではない。タスク固有の受け入れ条件（例: 「RAG の引用が残る」「GUI が期待した操作を行える」）も、テスト・スモーク・目視のいずれかで明示する。

## 1 変更の標準ループ

```text
タスクを整形
  → 現状を観測・再現
  → 最小変更とテスト
  → 段階的な検証
  → 要件から独立した差分レビュー
  → 証跡と学びの記録
  ↘ 失敗・不足した能力を発見したら、要件/テスト/ツールを補強して再試行
```

### 1. タスクを整形する

実装前に、少なくとも次を明文化する。PR 本文では [PR テンプレート](../.github/pull_request_template.md)を使う。

```text
Goal: 利用者に何ができるようになるか
Scope / non-goals: 触る範囲と意図的に触らない範囲
Acceptance criteria: 観測可能な完了条件
Verifier: その条件を確認するテスト、コマンド、または手順
Stop / escalation: 人の判断が必要になる条件
```

「GUI を良くする」ではなく、「編集後に Undo で直前のスライド状態が復元される。状態テストと GUI 契約テストで確認する」のように、判定可能な表現にする。

### 2. 観測してから変更する

- 最初に `git status --short` を確認し、他者の未コミット変更は所有しない。
- 変更対象の実装・近接テスト・対応するドキュメントを読む。
- バグなら、まず失敗を再現するテストまたは再現手順を残す。
- 入力例・ログ・生成物などに利用者文書の内容を記録しない。ローカル処理という製品原則を維持する。

### 3. 実装は境界を守って小さく行う

- LLM の出力、HTTP リクエスト、ファイル、テーマ、テンプレートは境界で検証する。
- 表示・PPTX・PDF のレイアウトはレンダラー側で決定し、モデルに任せない。
- 新しい振る舞いには、最も近い層の自動テストを加える。壊れたテストを削除・弱体化して通過させない。
- 実装上の繰り返しの迷いは、次回のためにユーティリティ、構造テスト、短いドキュメントのいずれかへ昇格させる。

### 4. 検証する

開発中は最速の関連テストを使う。完了宣言前には、必ず次を実行する。

```bash
npm run verify
```

このコマンドは次を固定順序で実行する。

1. `npm run lint`
2. `npm test`
3. `npm run smoke`
4. `npm run build`
5. `npm pack --dry-run`

追加で必要な証跡の例:

| 変更の種類 | 最低限の追加証跡 |
| --- | --- |
| スキーマ/API | 正常系・異常系の契約テスト |
| LLM/pipeline | モッククライアントを使う生成テスト |
| PPTX/HTML 表示 | 生成物の内容確認またはレンダリングテスト |
| GUI 操作 | 状態テストと HTTP/GUI 契約テスト |
| 文書解析/RAG | fixture と出典・メタデータの検証 |
| リリース設定 | `npm run verify` に加え、公開前の人による承認 |

### 5. 独立した観点でレビューする

実装したエージェント自身であっても、実装手順ではなく要件と差分から次を確認する。高リスクまたは大きい変更では別のエージェント/レビュアーに同じ観点を依頼する。

- 受け入れ条件を本当に満たしているか。
- 既存のローカル処理・入力検証・出力パス制限を弱めていないか。
- テストが実装をなぞるだけになっておらず、失敗した旧挙動を検出できるか。
- 必要な README / `docs/` の説明が更新されているか。
- スコープ外の変更、未検証領域、後続タスクを正直に残しているか。

## 失敗時の取り扱いと停止条件

失敗したら、同じ指示を無制限に繰り返さない。失敗コマンド・出力・仮説を残し、次のどれが不足しているかを特定する。

- 要件が曖昧または矛盾している
- 再現 fixture / テストが不足している
- リポジトリ知識や設計上の境界が不足している
- ツールや実行環境が不足している
- 人の製品判断または権限が必要である

次の場合は停止して人に判断を求める。npm 公開・リリース・push/merge、外部送信やプライバシー方針の変更、破壊的な互換性変更、要件を満たすことを検証できない場合である。

## 学習を次のループに残す

会話だけに結論を残さない。再発防止に有効なものは、優先順にテスト、機械的なチェック、対象モジュールのドキュメント、短い `AGENTS.md` の規則へ反映する。`AGENTS.md` は索引として短く保ち、詳細な設計知識は `docs/` に置く。

同じ種類の失敗が繰り返されてから、次の投資を行う。

- UI の手動確認が反復する: ブラウザ操作またはスクリーンショット検証を追加する。
- 依存方向の逸脱が反復する: 構造テストを追加する。
- ドキュメントの陳腐化が反復する: docs lint / 定期的な doc-gardening を導入する。
- CI 失敗の調査が反復する: 失敗ログから対象テスト・修復手順へ誘導するスクリプトを追加する。

この順序により、複雑な自律化を先に作るのではなく、実際に観測された摩擦だけをハーネスとして恒久化する。
